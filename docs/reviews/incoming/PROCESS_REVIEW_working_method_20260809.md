# 프로세스 리뷰 — 작업 방식 진단과 앞으로의 진행 가이드

- 날짜: 2026-08-09 KST
- 성격: 기술 검토가 아니라 **일하는 방식**에 대한 별도 리뷰
- 짝 문서: `EXTERNAL_REVIEW_mfa_r3_full_realign_20260809.md` (기술 검토 본문)

## 1. 진단 — 지금 어떤 식으로 작업하고 있는가

저장소의 결정문·감사 보고서·WORK_HISTORY를 시간순으로 보면 다음 패턴이
반복된다.

```text
진행 → 오류/의심 발견 → 전면 재점검 → 새 감사 스크립트·보고서·결정문 생성
  → 재점검 중 새 의심 발견 → 다시 재점검 → (원래 하려던 일은 아직 시작 전)
```

구체적 증거:

- **r3 준비가 21개 stage, readiness v1→v4, 결정문 약 18개**로 늘었다.
  특히 Stage 13–18은 사실상 한 가지 문제(zero-fallback hold의 회수)를
  6번의 개별 감사·결정 사이클로 나눠 처리했고, 각 사이클마다 새 스크립트와
  새 독립 감사기가 만들어졌다. 회수된 후보는 6,141형 + 14형 —
  85,000여 형의 7% 수준을 위해 6개 stage가 소요됐다.
- 2026-08-08 하루에 RESULT 결정문 15건 이상이 기록됐다. 각 단계가 "생성기
  + 독립 감사기 + 감사 보고서 + 결정문 + 현재상태 문서 갱신" 5종 산출물을
  요구하는 구조여서, 작은 전진 하나의 고정 비용이 매우 크다.
- `PROJECT_CURRENT_STATE.md`는 "누적 일지가 아니다"라는 자체 규칙(문서
  사용 규칙 §)에도 불구하고 300행이 넘는 stage별 서사가 됐다. 새 세션마다
  이 전부를 재독하는 비용이 발생한다.
- 안전검사·게이트가 늘면서(현재 PS 안전검사 allowlist 50개 파일, 토큰
  수백 개) 작은 스크립트 수정 하나가 여러 검사 파일의 토큰 갱신을
  연쇄적으로 요구한다.

**중요한 것: 이 방식이 실패한 것은 아니다.** r2 발음 배선 공백을 표본
검토가 실제로 잡아냈고, 원자료·보존 DB는 한 번도 오염되지 않았으며, 모든
후퇴는 증거를 남기고 이뤄졌다. 루프는 "무결성 비용"이지 무능이 아니다.
문제는 **비용 구조**다: 오류 1건의 발견이 즉시 전면 재점검을 트리거하고,
재점검이 새 의심을 낳는 재귀가 걸려 있어, 전진 단위당 비용이 단계가
갈수록 증가한다.

## 2. 루프의 구조적 원인 4가지

1. **심각도 분류 없는 즉시 회귀.** 오류가 발견되면 그것이 데이터를
   오염시키는 문제인지, 미래 구현에서 고치면 되는 문제인지, 기록만 하면
   되는 문제인지 분류하지 않고 즉시 현재 작업을 멈추고 되돌아간다.
   r2 발음 배선(진짜 Critical)과 사소한 표기 문제가 같은 강도의 대응을
   받는다.
2. **질문마다 새 도구.** "이 숫자가 맞나?"라는 질문이 생길 때마다 새
   전용 감사 스크립트 + 보고서 + 결정문이 만들어진다. 이미 130개가 넘는
   테스트와 수십 개의 감사 스크립트가 있는데도 유사 목적 스크립트가
   계속 추가된다. 도구를 만드는 일이 연구를 대체하는 상태다.
3. **done의 정의가 사후에 확장된다.** 한 단계를 끝냈다고 판단한 뒤에
   "그런데 이것도 확인해야 하지 않나"가 나오면 그 단계가 다시 열린다.
   Stage 12가 끝난 뒤 13이, 13이 끝난 뒤 14가 같은 hold 집합을 다시 여는
   식의 연장이 6회 반복됐다.
4. **모든 게이트가 직렬이다.** fail-closed 자체는 옳지만, 게이트가 모두
   순차 의존이어서 하나의 수정이 전체 체인의 재통과를 요구한다. 병렬로
   진행해도 되는 것(문서 정리, 테스트 배선, 계약 초안)까지 직렬 대기한다.

## 3. 앞으로의 작업 가이드

### 3.1 오류 대응 규칙 — "멈추는 오류"와 "적어두는 오류"를 구분한다

오류·의심 발견 시 다음 표로 **즉시 분류하고, 분류 결과에 따라서만**
행동한다. 분류에 1분 이상 쓰지 않는다.

| 등급 | 정의 | 행동 |
|---|---|---|
| STOP | 이미 생성된 정본 데이터를 오염시켰거나 오염 중 | 즉시 중단·격리·감사 (지금까지처럼) |
| FIX-NEXT | 아직 실행 전인 코드·계약의 결함 | **현재 작업 계속.** ERRATA 큐에 1줄 기록, 해당 구현 항목 차례에 수정 |
| RECORD | 표기·문서·명명 문제, 개선 아이디어 | ERRATA 큐에 1줄 기록만. 재점검 금지 |

이를 위해 `docs/ERRATA_r3.md` 한 파일을 만들어 append-only 큐로 쓴다.
형식은 `- [등급] 날짜 | 위치 | 한 줄 설명 | 처리 예정 지점`. 이번 외부
검토의 Critical/High가 아닌 지적들(M1–M9, L1–L3)도 이 큐로 들어가면 된다
— 전부 "FIX-NEXT"이며, 지금 되돌아가서 고칠 것이 하나도 없다.

### 3.2 전진 규칙 — 체크리스트 밖의 일을 하지 않는다

기술 검토 보고서 §7의 9항목 체크리스트가 2020 실행까지의 **전체** 작업
목록이다. 각 항목은 산출물과 통과 조건이 이미 정의돼 있다.

- 항목을 시작하기 전에 done 조건을 바꾸지 않는다. 작업 중 떠오른 추가
  요구는 ERRATA 큐로 보내고, 다음 release에서 다룬다.
- 한 항목이 끝나면 그 항목의 감사 1회로 닫는다. **같은 산출물의 재감사는
  입력 SHA가 바뀐 경우에만** 한다 — 이미 workflow §3에 있는 규칙이다.
  이 규칙을 문서만이 아니라 습관으로 지키는 것이 핵심이다.
- 새 스크립트를 만들기 전에 `scripts/SCRIPTS_INDEX.md`에서 기존 도구
  재사용 가능성을 먼저 확인한다. 새 단독 감사 스크립트는 체크리스트
  항목당 1개를 상한으로 한다.

### 3.3 문서 규칙 — 정본은 짧게, 서사는 히스토리로

- `PROJECT_CURRENT_STATE.md`를 실제 규칙대로 되돌린다: 연도별 상태 표 +
  현재 안전 정지점 + 다음 한 단계, 합계 60행 이내. Stage별 서사는 이미
  결정문에 있으므로 링크로 대체한다. (이 정리 자체도 r3 구현과 병렬로
  가능한 RECORD급 작업이다 — 지금 즉시 할 필요 없다.)
- 결정문은 "정책이 바뀔 때"만 만든다. 계산 결과 확인은 감사 보고서
  JSON으로 충분하며 별도 RESULT 결정문을 요구하지 않는다.

### 3.4 검증 규칙 — 기계 전수는 유지, 사람 반복과 도구 증식은 중단

- 유지: 연도별 독립 전수 감사, ID 회계 등식, SHA manifest, fail-closed
  게이트. 이것들이 지금까지 데이터를 지켰다.
- 중단: 같은 동결 산출물의 반복 재확인, 질문당 새 감사 스크립트, 이미
  통과한 표본의 재검토, 계약이 안 바뀐 상태의 새 파일럿. (모두 CLAUDE.md
  불변 규칙 9와 workflow §3에 이미 명문화돼 있다.)
- 사람(연구자) 개입은 RUNBOOK §8의 두 경우로만: 표본의 청취 확인, 장시간
  명령의 시작 승인.

### 3.5 한 문장 요약

> **오류는 큐에 쌓고, 전진은 체크리스트로만, 검증은 SHA가 바뀔 때만.**

## 4. 다른 도구에 수정안을 전달하는 방법

구현을 맡길 도구(Codex 등)에는 검토 보고서 전체를 요약해 주지 말고,
**체크리스트 항목 단위로 하나씩** 맡기는 것이 안전하다. 이유: (a) 항목마다
산출물·통과 조건이 이미 정의돼 있어 검증 가능한 단위가 되고, (b) 한 번에
전부 맡기면 도구가 r2 코드를 수정하는 지름길을 택할 위험이 커진다.

### 4.1 전달용 프롬프트 틀 (복사해서 사용)

첫 항목(v3.1 계약 개정) 예시. 이후 항목은 `[항목]` 부분만 바꾼다.

```text
C:\Users\ari30\research\2026_summer_research 저장소에서 작업한다.

먼저 다음 두 문서를 읽는다.
- docs/reviews/incoming/EXTERNAL_REVIEW_mfa_r3_full_realign_20260809.md
- docs/WORKFLOW_mfa_r3_full_realign_2020_2025.md

위 검토 보고서 §7 체크리스트의 [1번 항목: C2/M3 — v3.1 staged adoption
계약 개정과 승인 sidecar 분리]만 구현한다. 보고서의 해당 finding
(C2, M3)에 적힌 수정안과 통과 조건을 따른다.

제약:
- 체크리스트의 다른 항목을 미리 건드리지 않는다.
- 기존 r2 스크립트·r2 산출물·D: 자료·release Gate(allowed_release_ids)는
  수정하지 않는다. (Gate 개방은 8번 항목에서만.)
- Stage 01–21 산출물을 재생성하지 않는다.
- 새 .ps1은 UTF-8 BOM, PowerShell 5.1 규칙(AGENTS.md)을 따르고
  tests/test_powershell_safety.ps1 allowlist에 추가한다.
- 작업 후: 변경 파일 목록, 통과 조건 충족 근거, 실행한 테스트 결과를
  보고하고, 발견한 추가 문제는 고치지 말고 docs/ERRATA_r3.md에 기록한다.
```

### 4.2 전달 순서와 검수 방법

1. 항목 1–4(계약·builder 층)는 계산이 가벼우므로 연속으로 맡겨도 된다.
   항목마다 끝나면 **통과 조건만** 확인하고 다음으로 넘어간다(전체 코드
   재검토 금지 — 그것이 다시 루프를 만든다).
2. 항목 5(runner)는 가장 크므로 별도 세션으로 맡기고, 완료 후
   `-PreflightOnly` 실행 결과 JSON만 확인한다.
3. 항목 7(테스트 배선)까지 끝난 뒤, 원하면 이 검토를 수행한 도구에게
   "체크리스트 1–7 구현 결과가 보고서의 통과 조건을 충족하는지"의 좁은
   재검토를 1회 요청한다. 재검토 범위는 신규·수정 파일로 한정한다.
4. 항목 8(Gate 개방)과 9(2020 preflight GO)는 연구자가 직접 확인 후
   진행한다 — 이 두 개만이 사람의 결정 지점이다.

### 4.3 하지 말 것

- 검토 보고서를 요약·의역해서 전달하지 않는다. 경로를 주고 읽게 한다
  (의역 과정에서 통과 조건이 소실된다).
- "겸사겸사 이것도" 식의 범위 확장을 지시에 넣지 않는다.
- 구현 도구가 보고한 "추가로 발견한 문제"에 즉시 반응하지 않는다 —
  ERRATA 큐로 보내고 현재 항목을 끝낸다 (§3.1 규칙과 동일).
