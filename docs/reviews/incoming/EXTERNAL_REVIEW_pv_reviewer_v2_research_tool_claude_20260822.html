4. 현재 설계에서 유지할 부분

다음은 실측으로 확인했고 그대로 유지할 것을 권고한다(변경 불필요).

1. 한 후보 한 화면 + 좌측 후보 목록·검색·핵심/탐색 필터·이전/다음. v1의 최다 불만(세로 나열, 위치 파악 불가)에 대한 해법이 의도대로 구현됨.
2. append-only 보존 회계. v1 15행 byte-for-byte 보존(SHA 동일), 의미상 중복 1행 비삭제, possible_duplicate_of는 표시일 뿐 삭제 기능 없음, revision은 event_uuid·supersedes_event_uuid 사슬로 연결.
3. 자동 판정 아님의 3중 명시. 헤더 문구, 형태소 카드의 "검색 환경 근거" 문구, 발음 패널의 "실제 들린 발음이나 자동 실현 정답이 아님" 경고, 그리고 모든 revision 행의 record_role='exploratory_pv_only_not_formal_realization_ledger'. 정식 ledger 혼동 위험은 현 설계에서 낮다.
4. 문헌 연결 규칙. not_found 1행과 원문 미확인 재인용 10행을 긍정 목록에서 제외하는 규칙이 코드·감사·실측 회계(40→29)에서 모두 일치. 원유권(2022)을 후보별 현상 근거가 아니라 공통 방법론 패널에만 연결한 결정도 유지.
5. 사회정보·발음 참조의 접힘 기본값. 청취 전에 성별·연령·지역·예상 발음이 보이면 실현 인상에 선입견을 줄 수 있다. 접힘 + 패널 노출 자동 기록(reference_panels_viewed_json, context_viewed)은 편향 통제와 사용 기록을 동시에 얻는 좋은 설계다. 이 로그가 있어서 AFTER_30 결정(R10·R11)을 실사용 데이터로 내릴 수 있다.
6. 전체 대화는 텍스트만, 오디오는 대상·±2만. 크기·출처 회계 유지. 기본 ±10행 표시 후 검색·전체 보기로 확장하는 점진 공개도 적절.
7. zero-drop 회계. PV0027의 form_tagged_count_mismatch를 자동 보정 없이 상태로 보존·표시하는 원칙 자체는 옳다(표시 문구만 R08).
8. ±2 문맥 전사 패널과 전체 대화 패널의 분리. 중복처럼 보이지만 ±2 표는 음성 bundle과 1:1인 회계 정보(slot/wav 상태)를 보이므로 통합하지 않는 편이 단순하다.

5. NOW_BLOCKER — 30개 작업 전 반드시 처리

NOW_BLOCKER · P0R01 저장하지 않은 입력이 이동 시 경고 없이 사라짐 (확인된 결함)

  • 근거: HTML 스크립트의 setActive()가 후보 전환 시 무조건 restoreForm()→form.reset()을 실행하며, 이전/다음 버튼·후보 버튼·가져오기 어디에도 dirty 상태 확인이 없다(builder 내장 템플릿에서 확인).
  • 실패 시나리오: 약 1시간 세션에서 메모를 길게 쓴 뒤 "새 revision 저장" 대신 "다음 →"을 누르면 입력 전체가 조용히 사라진다. 30개×연 6개 규모에서는 거의 확실히 발생한다.
  • 권고: 입력 변경 플래그를 두고, 미저장 상태에서 후보 이동·가져오기 시 확인창(저장 후 이동/버리고 이동)을 띄운다. 몇 줄 수준의 변경.
  • 더 단순한 대안: "이동 전 반드시 저장" 운영 습관만으로도 줄일 수 있으나, 1시간 단위 반복 작업에서 습관에만 의존하는 것은 P0 위험을 남긴다.

NOW_BLOCKER · P0R02 localStorage 단일 사본에 의존하지 않는 내보내기 규칙 (운영 규칙)

  • 근거: 저장된 revision은 브라우저 localStorage(pv_reviewer_v2_local_history_20260822)에만 존재하고, 내보내기 전에는 파일이 없다. localStorage는 기기·브라우저별로 분리되고, iPad Safari 계열은 저장 공간 축출 가능성이 문헌상 알려져 있다(이 환경에서 재현 실험은 하지 않았다). HTML을 Dropbox로 옮겨도 기록은 따라가지 않는다.
  • 권고(코드 변경 없이 즉시 채택 가능한 운영 규칙): ① 검토 세션을 끝낼 때마다 "전체 JSONL 저장"(iPad에서 실패 시 복사용 패널)으로 내보내고 Dropbox 배치 폴더에 둔다. ② 한 시점에는 한 기기에서만 작업한다. ③ 배치당 내보내기 JSONL은 1개 흐름으로 유지하고, 기기를 바꿀 때는 직전 내보내기를 가져온 뒤 시작한다. ④ 배치 간 병합은 HTML 안에서 하지 않고 오프라인 분석 단계로 미룬다.
  • 이 규칙은 v1에서 사용자가 이미 수행한 흐름(내보내기→Dropbox)의 명문화이며, 기존 Dropbox 상위 폴더 정리 규칙과도 맞는다.

NOW_BLOCKER · P1R03 파라미터화된 batch builder + 약 1시간 batch manifest (확대 전제)

  • 근거: 현 builder는 pick_balanced_samples 14개, 사용자 JSONL "15행·고유 14" 계약, 2020/2025 endpoint를 하드코딩한 단일 목적 스크립트다(의도된 좁힘이며 결함이 아님). 연도별 30개는 이 스크립트로 생성할 수 없다.
  • 권고: 기존 v2 파일을 수정하지 말고, 같은 HTML 템플릿·기록 schema를 재사용하는 새 batch builder를 추가한다. batch manifest에는 최소한 다음을 넣는다: batch_id, 후보 pv_id 목록, 연도·현상 쿼터, 표본별 대상·±2 길이 합산으로 추정한 예상 청취 시간(약 1시간 상한), zero-drop 상태, 산출 HTML의 bytes·SHA-256, 이전 배치 JSONL의 SHA(이어서 검토할 때).
  • HTML 크기 상한도 여기서 정한다: 이번 14개가 오디오 소스 8.66MB→HTML 19.5MB였으므로, 배치를 시간 기준으로 나누면 자연히 파일도 iPad에서 다루기 쉬운 크기로 유지된다.
  • 사용자 결정 필요: 연 30개를 몇 배치로 나눌지(예: 예상 청취 시간 합산 기준 2–3배치), 연도 진행 순서.

NOW_BLOCKER · P1R04 대화 텍스트 스캔의 연 200,000행 상한 계약 개정 (사용자 결정)

  • 근거(실측): 이번 14개는 target이 2020년 표의 60,194행, 2025년 표의 12,504행 안에서 발견되어 상한이 문제되지 않았고, 14개 대화 모두 utt_seq 조밀성으로 완전함을 확인했다. 그러나 연도별 30개는 연도 표 전체(수십만~백만 행대)에서 뽑히므로, 상한 200,000행 밖의 표본은 target_not_found_within_cap으로 zero-drop 보존은 되지만 대화 패널·화자 묶음·사회정보가 비게 된다. 확대 후 도구 가치의 큰 부분이 사라진다.
  • 권고: "자동 상한 확대 금지" 원칙은 유지하되, 30개 빌드에 한해 명시적 승인으로 스캔 계약을 바꾼다. 더 단순하고 안전한 방식은 상한을 키우는 것이 아니라 2-pass 대상 한정 스캔이다: 1차로 target utt_id 행만 찾아 세션 키를 얻고, 2차로 파일 전체를 스트리밍하되 그 세션 키에 속한 행만 보유한다. 메모리 사용은 지금과 같은 수준이고, 상한은 "보유 행 수"가 아니라 "대상 세션 수"로 걸린다.
  • 사용자 결정 필요: 이 계약 변경(연 전체 스트리밍 스캔 허용) 승인 여부.

  • 권고: 배치별 빌드에서 localStorage 키·ipad_batch·내보내기 파일명에 batch_id를 넣고, revision 행에 reviewer(및 선택적으로 기기 표지) 필드를 복원한다. 화면에는 "내보내지 않은 revision N개"를 상시 표시한다.

NOW_SMALL · P1R06 표적 어절 시각 강조 (설계 대비 미구현)

  • 근거: 승인 설계 §4.2는 "색으로 강조한 표적 어절"을 항상 보이는 최소 정보로 명시했으나, 구현은 발화 전문을 평문으로만 표시한다(active-form에 textContent 대입, 강조 마크 없음). v1 최다 요구가 "무엇을 들어야 하는지 찾기 어렵다"였다. 이번 사용자 3표본에서 불편이 없었던 것은 PV0001이 단일 어절(6자)인 등 짧은 표본이었기 때문이며, 2025 표본은 71자(PV0151)까지 있다.
  • 권고: 동결 PV_SAMPLES.csv에 이미 있는 target_word_indices_json·target_word_labels_json을 payload에 넣어 발화 내 해당 어절을 <mark>로 강조한다. 새 분석이 필요 없는 읽기 전용 표시 변경이다. 규칙 예상형·사전 참조형 문자열에도 같은 위치 강조를 적용하면 장문 비교가 쉬워진다(부수 효과, 선택).

NOW_SMALL · P1R07 최신 revision 계산이 배열 순서 기준 (확인된 결함)

  • 근거: latestByEvent()가 시각이 아니라 배열 순서(마지막 행 우선)로 최신을 고른다. 가져오기는 행을 목록 끝에 추가하므로, 새 revision을 만든 뒤 더 오래된 내보내기를 가져오면 오래된 행이 "최신"으로 표시되어 폼 복원·완료 체크·진행률이 과거 값으로 돌아간다(원행 손실은 없음).
  • 권고: 최신 선택을 reviewed_at 우선(동률이면 배열 순서)으로 바꾼다.
  • 더 단순한 대안: "가져오기는 항상 시간순으로만 한다"는 운영 규칙(R02의 확장). 단일 기기 운영이면 발생하지 않는다.

NOW_SMALL · P2R08 상태 코드에 한국어 설명 병기

  • 근거: 화면에 unavailable_form_tagged_count_mismatch_zero_drop 같은 내부 코드가 원문 그대로 노출된다(PV0027). 정확하지만 연구자가 매번 해석해야 한다. HIA 축약형(PV0177 '돼')에는 "경계 돼"라는 라벨이 붙는데 이는 경계가 아니라 축약 음절이다.
  • 권고: 코드값은 그대로 두고 옆에 한국어 한 줄을 병기한다. 예: PV0027 → "표기 어절 수와 형태소 분석 어절 수가 달라 형태소를 연결하지 않았습니다. 후보는 삭제 없이 유지됩니다." HIA kind에는 "경계" 대신 "축약 음절" 라벨.

NOW_SMALL · P2R09 '판단 확신도' 라벨 명확화

  • 근거: 폼에 환경 인상·실현 인상·들린 형식이 함께 있어 "판단 확신도"가 어느 판단의 확신도인지 모호하다(필드명 judgement_confidence).
  • 권고: 라벨을 "들린 형식·실현 인상에 대한 확신도"로 바꾼다(필드명은 유지해 schema 변경 없음). 실현·불확실성·겹침·문맥·음질의 다른 필드 분리는 현행이 적절하다.

10. 더 단순한 운영안

localStorage·Dropbox 질문(핵심 질문 10·11)에 대한 권고 운영 모델:

  1. 배치 = 파일. 한 배치는 HTML 1개 + 내보내기 JSONL 1개 흐름으로 관리한다. localStorage는 세션 중 임시 버퍼로만 취급한다(R02).
  2. Dropbox 규칙. 기존 상위 폴더 하나 아래 배치별 하위 폴더를 두고, HTML·내보내기 JSONL·batch manifest를 함께 둔다.
  3. 세션 리듬. 열기 → (기기를 바꿨으면 직전 JSONL 가져오기) → 청취·저장 반복 → 종료 전 내보내기 → Dropbox 저장. 약 1시간 상한은 batch manifest가 보장하므로 도구 쪽 타이머는 불필요.
  4. 재개. 같은 기기면 localStorage로 즉시 재개, 기기가 바뀌면 가져오기로 재개. 진행률·완료 체크는 현행 표시로 충분하다.
  5. 병합·정본화. 배치 JSONL들의 병합, 최신 view 재구성, 정식 실현 판정 ledger로의 승격은 전부 HTML 밖 오프라인 단계에서 한다(R13). reviewer HTML은 끝까지 탐색 기록 도구로만 남긴다.

  2. R03: 연 30개의 배치 구성(예상 청취 시간 합산 약 1시간 기준 몇 배치로 나눌지)과 연도 진행 순서.

  4. R02 운영 규칙 채택: 세션마다 내보내기·한 시점 한 기기·배치당 JSONL 1개 규칙의 채택.

  2. v2.1 파생 재빌드: R01(dirty guard)·R05(batch_id·reviewer·카운터)·R06(표적 강조)·R08(한국어 병기)·R09(라벨) + R07(최신값 정렬). 기존 v2 root는 무수정 보존, 새 root + 독립 감사 + SHA manifest.

13. 미해결 위험과 검토 한계

  • 실기기 검사 없음. iPad Safari·노트북 브라우저에서의 실제 렌더링·저장 지속성은 이번에도 검사하지 못했다(구현 세션의 인앱 브라우저도 trusted-path 오류로 실패). 사용자 3표본 Gate의 사용성 확인에 의존한다.
  • localStorage 지속성은 문헌상 위험. iOS 저장 축출을 이 환경에서 재현하지 않았다. R02가 방어책이며, 축출이 실제로 관찰되면 R05의 카운터가 손실 범위를 알려 준다.
  • 대화 완전성은 간접 검증. utt_seq 1..N 조밀성으로 확인했고 원천 CSV 전량 재대조는 D: 대량 I/O를 피하기 위해 하지 않았다(감사기도 영수증 수치 대조까지 수행). 조밀성 검증은 향후 감사기에 추가할 가치가 있다.
  • 문헌 40행의 내용 정확성은 기존 승인 AUDIT에 의존. 이번 검토는 회계(40→29 제외 규칙)만 재확인했고 원문 대조는 범위 밖이다.
  • 음성 청취 평가는 하지 않았다. 세 표본의 소리·판정 자체는 검토 범위 밖이며 자동 실현 판정도 하지 않았다.
  • JS 검토는 정적 읽기 기준. runtime 시험(통과 기록)과 코드 정독으로 판단했고, 브라우저 실행 검증은 하지 않았다. R01·R07은 코드 경로가 명확해 확인된 결함으로 분류했다.
