# 완료 소스의 무손실 압축 강도 비교

2026-10-17 사용자가 즉시 시험할 수 있는 속도 개선 방법을 요청해, 활성 보강 코드를 유지한 상태에서 완료된 두 소스의 압축 출력 6개를 제한된 별도 시험으로 비교했다. 전체 보강 작업자를 추가로 실행하지 않았다.

현재 생산 저장 코드는 기본 gzip 강도 9를 사용한다. 각 입력을 해시 영수증과 대조하고, 압축을 풀어 얻은 동일 바이트를 강도 1·3·6·9로 각각 두 번씩 순서를 바꾸어 메모리에서 재압축했다. 모든 48회 복원의 바이트와 해시가 원본과 같았고 입력 파일은 그대로 유지됐다. 강도 9의 압축 바이트도 기존 생산 출력과 정확히 같았다.

| 강도 | 표본별 압축 시간, 기존 강도 9 대비 | 압축 파일 크기 변화 |
| --- | --- | --- |
| 6 | 약 1.4–2.5배 빠름 | 약 3–4% 증가 |
| 3 | 약 3.8–5.1배 빠름 | 약 33–35% 증가 |

강도 3에서 소스 하나의 세 출력을 합친 압축 시간 절감은 각각 약 0.52초와 0.23초였다. 측정한 것은 압축 구간이며, 사전 적용·DB 조회·직렬화·해시·디스크 입출력·감사는 포함하지 않는다. 두 소스의 작은 표본과 동시 생산 작업의 영향을 받으므로 전체 속도 향상률이나 완료일 단축으로 외삽하지 않는다.

여유 메모리가 약 1GB였으므로 추가 전체 작업자나 사전 모델을 띄우지 않았다. 시험은 낮은 프로세스 우선순위, 700MiB 여유 메모리 하한, 파일당 최대 32MiB 복원, 전체 60초 확인 한도를 사용했다. 실제 두 시험은 각각 약 2.92초와 1.75초였다. 합성 검사 5개는 복원 동일성·원본 보존·해시 불일치·상위 경로·복원 크기·메모리 하한을 확인했다.

현재 실행의 코드·계약·장부·출력은 변경하지 않았다. 압축 강도 변경도 출력 해시와 코드 계약을 바꾸므로 현재 수정판에 몰래 섞지 않는다. 현재 근거로는 진행 중인 작업을 중단·재구성할 만큼의 전체 시간 이득이 입증되지 않았다. 강도 6은 다음 저장 실행에서 검토할 수 있는 작은 크기 증가의 후보이며, 큰 단축을 목표로 한다면 DB 조회·규칙 적용 등 전체 구간 시간 계측이 먼저 필요하다.

재사용 도구는 [제한된 압축 비교기](../../scripts/python/benchmark_lossless_gzip.py), 합성 검사는 [검사 코드](../../tests/test_benchmark_lossless_gzip.py)다. 실제 표본과 상세 측정 영수증은 로컬에 보존한다. 이 게시에는 원문이나 실제 발화 식별자가 포함되지 않는다.
