## 이번에 드러난 운영상 문제

- 프로세스가 비정상 종료하면 STATE에 과거 running이 남을 수 있다. 상태 문자열과 오류 로그 크기만으로 실행 상태를 판단하면 안 된다.
- 재개 초기에는 완료 산출물의 해시를 검사하지만 새 요청 직전까지 STATE 갱신이 없다. 이 기간은 프로세스의 생성 시각·실행 명령·CPU 시간·읽기 바이트 증가로 실제 진행을 확인했다.
- 정기 보고 자동화가 예정 시각보다 몇 분 일찍 실행되기도 했다. 조기 실행을 무조건 생략하는 지시 때문에 사용자에게 약속한 보고 일부가 누락됐다.

## 현재 복구 절차

1. 같은 계약·출력 폴더·볼륨과 OS 독점 잠금을 확인하고 활성 분석기가 있으면 중복 실행하지 않는다.
2. 읽기 전용 장부에서 complete와 reserved를 나눠 확인한다. 예약 건수를 완료 건수에 합치지 않는다.
3. 응답 파일이 있으면 원 입력·본문 해시·응답 해시를 검증하고 저장 응답을 재사용한다.
4. 응답 없는 전송은 서버 처리 여부가 불명이다. 해당 요청에 대한 사용자 승인 후 원 전송 의도·오류·승인·중복 차감 추정치를 보존하고 검증된 단건 실행기를 사용한다.
5. 단건 응답 저장 성공과 후속 신규 완료 증가를 각각 확인한다. 재개 프로세스 시작만으로 신규 처리가 시작됐다고 보고하지 않는다.
6. 신규 실행에서 다시 실패하면 새 오류와 불명 요청을 보존한다. 기존 단건 승인을 다음 실패의 자동 재전송 승인으로 확대하지 않는다.

## 전수 종료 후 구현할 보완

활성 분석기와 고정 계약은 유지하고, 종료 후 별도 수정판에서 다음을 구현·검증한다.

- 감독기가 자식 종료 코드·종료 시각을 별도 상태에 남기고 비정상 종료를 탐지한다. 마지막 불명 요청과 재개 가능 여부를 기록한다.
- 검증/저장/API 호출/최종 감사 단계를 구분하고 기존 결과 검증 중에도 최근 진행 시각·검사한 소스 수를 갱신한다.
- 원 요청과 시도별 기록을 연결해 전송 의도·응답·실패·명시적 재시도·중복 사용량 추정을 보존한다.
- 상태가 오래됐을 때 프로세스 및 진척 증거를 확인하고, 무조건 재시작하거나 정지로 단정하지 않는다. 검증 단계와 장시간 요청의 정상 소요를 고려한다.
- 감독기 강제 종료, HTTP 503, 응답 저장 직후 종료, 재개 중 재종료를 합성 입력으로 검증한다. 완료 응답 재전송과 예약 건수 누락을 검사한다.
- 정기 보고는 예정 슬롯의 전후 10분을 허용하고 슬롯당 한 번 보고한다. 실제 보고 시각을 표시하고 마지막 보고 슬롯을 보존한다.

이 문서는 사고 이력과 검증할 개선 요구다. 위 예방 기능 전체가 현재 실행기에 구현됐다는 의미는 아니다. 전수 감사 및 검색 개선 뒤 공개 가능한 코드·시험·문서만 GitHub 게시 대상으로 검토한다.
